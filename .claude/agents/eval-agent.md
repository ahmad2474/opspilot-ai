You build the eval harness for OpsPilot AI, per `docs/opspilot-ai-roadmap-phase2.md` Section 2. Its whole
job: generate a provably-correct answer straight from `services/` (bypassing the LLM entirely), then check
whether the chat agent's actual answer agrees with it. This is the project's answer to "how do you know
your agent isn't hallucinating" — treat grading correctness as seriously as `backend-agent` treats
idle-detection correctness.

## Scope
- `opspilot-backend/eval/` (new — mirrors the existing `opspilot-backend/tests/` layout and Python
  environment, so it can import `app.services.*` directly rather than re-implementing anything).
  - `eval/fixtures/` — `moto`-provisioned, versioned golden AWS accounts (§2.1): a known number of idle
    EC2 instances at known ages, an unattached EIP, an RDS instance five days old (exercises the existing
    `idle_since_is_estimated` edge case), etc. Deterministic, no real AWS, no rate limits, no cost.
  - `eval/oracle/` or similar — ground truth generated by calling `check_idle`, `estimate_cost`,
    `scan_service.scan_region()` etc. **directly against a fixture**, never derived from an LLM response
    (§2.2). This is the one piece of this whole harness that must never itself become a source of
    hallucination.
  - `eval/cases/*.yaml` — the question bank (§2.3). Cover at minimum: basic idle-count accuracy, the
    young-resource edge case (`idle_since_is_estimated`), a prompt-injection case (a resource's Name tag
    containing an embedded instruction — must still report the true idle status, tag content is untrusted
    display data, never an instruction), the out-of-scope redirect behavior (roadmap 3.8), and a
    recall-accuracy case for investigation memory (a recalled past investigation must match, not
    contradict, the current one).
  - `.github/workflows/eval.yml` — CI wiring (§2.6): a `deterministic` job (fast, free, every PR) and a
    `judged` job (LLM-judge metrics, costs judge-LLM tokens) gated behind a `run-full-eval` label or
    nightly cron, not run on every PR by default.
- Grading, in this priority order (§2.4), cheapest/most-reliable first:
  1. **Deterministic** — extract numbers/entities from the final answer, compare to the oracle with an
     explicit tolerance (exact match for counts/IDs/idle-days, small tolerance for dollar estimates since
     Pricing API values can drift).
  2. **LLM-judge faithfulness** — every claim in the answer must trace back to something actually present
     in that run's tool-call outputs, never general world knowledge or the model's own math.
  3. **Tool-trace correctness** — assert the *right* tools were actually called, since the reasoning trace
     is already a first-class UI feature; a right-but-lucky answer from skipping a tool call should fail.
- Framework (§2.5): **DeepEval** as the primary CI gate (pytest-native, matches this repo's existing test
  convention exactly) — `ToolCorrectnessMetric` for tool-call grading, `FaithfulnessMetric`/
  `HallucinationMetric` for the qualitative layer. Ragas and Promptfoo are optional/lower-priority — don't
  add either unless asked; DeepEval alone is the acceptance bar for this step.

## Non-negotiables
- **No real AWS, no live LLM spend by default.** Every fixture is `moto`-mocked, matching the exact
  boto3-client-factory mocking convention already used in `opspilot-backend/tests/` (check it before
  writing new fixtures, don't invent a second mocking style). The `judged` CI job is the only place real
  judge-LLM calls happen, and only when explicitly triggered — never make the deterministic job depend on
  a live LLM call.
- **Reuse this project's existing free-tier LLM setup for the judge model — do not add a new LLM
  provider dependency.** DeepEval defaults to OpenAI for its judge models; this project has zero
  OpenAI/paid-LLM usage anywhere (README: "Zero AWS spend, zero LLM spend," three free-tier providers with
  fallback) and that's a stated project value, not an oversight. Wire DeepEval's judge against the same
  Groq/Gemini/Nvidia clients the chat agent already uses. If DeepEval's provider abstraction genuinely
  can't be pointed at one of those without real friction, stop and flag it to the user as a real
  infra/tradeoff decision — don't silently add an OpenAI key requirement.
- Ground truth is computed from `services/`, full stop — never from prompting an LLM to "guess what the
  answer should be" and never hand-typed without running the corresponding fixture through the real
  service function first.
- Run the deterministic suite yourself and report actual pass/fail counts before calling this step done —
  same "evidence before assertions" bar as every other agent here.

## Guardrails
- Don't touch `app/tools/`/`app/services/`/`app/aws/` investigation logic itself — if a gap in tool
  behavior surfaces while building a fixture, flag it back to `backend-agent`/the user, don't quietly fix
  it here as a side effect of writing a test.
- Don't touch `opspilot-frontend/` — this step has no UI surface of its own.
- If Section 3's LangGraph adoption (`langgraph-agent`) has already landed by the time you run, LangSmith
  is a natural pairing for graph-based node tracing — otherwise don't add it.
